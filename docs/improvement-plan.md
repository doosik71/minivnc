# MiniVNC 처리 속도 개선 계획

작성일: 2026-11-03 (Asia/Seoul)  
분석 대상: D:\dev\minivnc의 Rust 구현 및 D:\dev\minivnc\turbovnc의 TurboVNC 3.3.2 참고 소스  
범위: libjpeg-turbo 도입을 전제로 한 서버 캡처·동시성·전송·영역 처리와 클라이언트 수신·디코딩·렌더링. 인코더 내부 개선은 연계 항목으로만 정리한다.

## 1. 결론과 전제

우선순위는 측정 분리 → 불필요한 복사와 메타데이터 누적 제거 → 수신 버퍼 개선 → 캡처 왕복 및 잠금 시간 단축 → 뷰어 부분 갱신 → 파이프라인 조정이다. 언어 교체나 스레드 수 증가만으로 TurboVNC보다 빨라질 것으로 가정하지 않는다.

이 문서는 소스를 읽어 확인한 구조와 개선 제안이다. 빌드·실행·벤치마크를 수행하지 않았으며, 속도 향상 배수나 FPS는 검증되지 않았다. 다른 에이전트가 개발 중이므로 함수명과 동작을 다시 확인한 뒤 구현한다. 문서 작성 과정에서는 소스·설정·git 상태를 변경하지 않는다.

성공 기준은 같은 화질·작업량에서 CPU 시간, 복사 바이트, 할당, 화면 반영 지연을 줄이는 것이다. 업데이트 수 증가나 전송 화질 저하만으로 성공을 판정하지 않는다.

## 2. 현재 경로와 이미 구현된 기능

서버 경로:

XDamage → XShm/GetImage → 임시 픽셀 버퍼 → screen.plain → screen.drawn → 클라이언트별 영역/Interframe 처리 → 인코딩 → 전체 업데이트 버퍼 → 소켓/TLS

뷰어 경로:

소켓/TLS → RFB 파싱 → 사각형 디코딩 → 클라이언트 프레임버퍼 → SharedScreen → softbuffer 가시 영역 복사 → present

확인한 기존 기능은 유지하고 중복 구현하지 않는다.

- XDamage와 MIT-SHM, SHM 불가 시 GetImage 대체 경로
- 클라이언트별 수정 영역, Continuous Updates, Fence 기반 혼잡 제어
- 최대 4개 작업으로 나누는 Tight 병렬 인코딩, Interframe Comparison, ALR
- 뷰어의 비-CU 업데이트 요청 파이프라이닝과 damage 알림 중복 억제
- TLS 읽기 대기 시 잠금을 풀려는 기존 처리

주의: CAPTURE_POLL=200ms는 wait_changes의 대기 상한이며 고정 캡처 간격이 아니다. X 이벤트는 대기를 깨운다. POINTER_POLL=10ms도 화면 전체의 100FPS 제한을 뜻하지 않는다. TurboVNC Xvnc 내부 대기 기본값 40ms와 달리 일반 vncserver 스크립트는 -deferupdate 1을 전달한다. 비교 시 실행 인자를 맞춘다.

## 4. 개선 항목

### 4.1 구간별 계측을 먼저 분리한다 (P0)

근거: crates/rfb-server/src/session.rs의 Profile::record와 send_update. 현재 로그의 encode 시간에는 encode_update뿐 아니라 write_all 및 flush를 기다린 시간도 포함된다. 이를 순수 인코딩 CPU 시간으로 해석하면 안 된다.

제안:

- 캡처 이벤트 대기, X 요청/응답, 픽셀 복사, 화면 잠금 획득/유지, Region/Interframe, 순수 인코딩, 소켓 쓰기 대기를 따로 측정한다.
- 뷰어는 수신 대기, 파싱, 디코딩, SharedScreen 복사/잠금, 렌더 복사, present를 구분한다.
- 업데이트별 세대 번호, 변경 픽셀 수, 인코딩 픽셀 수, 전송 바이트, 사각형 수, 큐 깊이, 재동기화 횟수를 집계한다.
- p50/p95/p99 지연과 장시간 RSS를 기록한다. 상세 이벤트 로그는 선택적으로 켜고 기본은 집계한다.
- 서버와 클라이언트의 단조 시계는 그대로 뺄 수 없다. 종단 지연은 동기화된 계측 또는 입력/표시 왕복 측정으로 구한다.

완료 기준: 순수 CPU 병목과 네트워크 대기 병목을 구분할 수 있고, 계측 활성/비활성 오버헤드를 보고한다.

### 4.2 ALR 비활성 시 lossy 사각형 기록을 누적하지 않는다 (P0)

근거: TightEncoder::send_jpeg는 self.lossy에 사각형을 추가하고 encode는 작업별 기록을 합친다. 반면 session.rs의 encode_update에서는 config.alr.is_some()일 때만 take_lossy를 호출한다. 확인한 호출 경로에서는 ALR가 꺼져 있어도 JPEG 사각형 메타데이터가 연결 수명 동안 누적될 수 있다.

제안:

- 업데이트마다 기록을 소비하고 ALR 비활성 시 버리거나, ALR 추적이 필요한 경우에만 기록한다.
- 기록 초기화와 ALR 실제 lossy Region 갱신을 분리하고, 반복 할당을 피하도록 용량 재사용을 검토한다.
- JPEG 출력·화질과 관계없는 수명 관리 수정으로 별도 구현한다.

완료 기준: ALR off/on 각각 영상 업데이트 10만 회 후 내부 기록이 무제한 증가하지 않는다. 장시간 RSS가 안정되고 ALR on의 최종 무손실 복원은 유지된다. RSS가 즉시 감소해야 한다는 조건은 두지 않는다.

### 4.3 XShm부터 프레임버퍼까지의 임시 버퍼를 없앤다 (P1)

근거: capture-x11/src/x11/capture.rs의 get_image는 SHM 데이터를 to_vec로 복사한다. read는 그 결과를 fb.put_rect로 다시 복사한다. rfb-server/src/lib.rs의 copy_region도 행들을 임시 Vec에 모은 뒤 drawn에 복사한다.

제안:

- SHM 응답 완료 후 공유 메모리의 각 행을 목적 프레임버퍼 행으로 직접 복사한다. 패딩이 있으면 유효 픽셀 바이트만 복사한다.
- copy_region은 임시 Vec 없이 서로 다른 프레임버퍼 사이에서 행 단위 copy_from_slice를 수행한다.
- GetImage 대체 경로는 응답 데이터에서 목적 행으로 직접 옮긴다.
- mapped SHM을 인코더에 바로 노출하는 전면 zero-copy는 후순위로 둔다. 다음 X 요청이 메모리를 덮어쓸 수 있으므로 수명·소유권 검증이 선행되어야 한다.

완료 기준: 캡처/커서 복사용 사각형 임시 할당이 사라지고, 16/32bpp·행 패딩·리사이즈·SHM 대체 경로의 픽셀이 기존 결과와 일치한다.

### 4.4 소프트웨어 커서용 drawn 버퍼를 필요할 때만 유지한다 (P1)

근거: apply는 커서 모양을 별도로 처리하는 클라이언트만 있어도 plain에서 drawn으로 변경 영역을 복사한다.

제안:

- 서버 합성 커서가 필요한 연결 수를 추적하고, 그런 연결이 없으면 drawn의 상시 갱신을 생략한다.
- 최초 필요 연결 또는 커서 인코딩 협상 변경 시 최신 plain에서 drawn을 초기화한다.
- 화면 변경과 커서 이전/새 위치의 합집합을 올바르게 복원한다. 연결 종료·리사이즈·커서 숨김 전환도 처리한다.

완료 기준: 하드웨어/로컬 커서 처리만 필요한 연결에서는 drawn 복사량이 제거되고, 혼합 연결의 커서 잔상 및 누락이 없다.

### 4.5 XDamage를 일괄 결합하고 캡처 사각형을 비용으로 선택한다 (P1)

근거: wait_changes는 DamageNotify마다 Region::union을 수행한다. Region::op/span_op는 경계 배열을 만들고 정렬한다. read는 사각형마다 동기 X 응답을 기다리며 100개 초과 시 bounding box로 합친다. 서버 업데이트에도 100개 기준이 있지만, 캡처 왕복 비용과 인코딩 비용은 서로 다르다.

제안:

- 한 이벤트 배치의 damage 사각형을 모아서 정규화하고, 기존 정규 Region의 정렬 상태를 이용하는 선형 병합을 검토한다.
- 빈 영역·서로 분리된 단순 영역의 빠른 경로와 작업 버퍼 재사용부터 적용한다.
- 캡처는 대략 N×요청 왕복 비용 + 읽을 바이트/유효 처리량으로 개별 사각형·그룹 경계 상자·전체 경계 상자를 비교한다.
- 과잉 캡처 비율도 제한한다. 멀리 떨어진 작은 변경을 무조건 전체 화면으로 합치지 않는다.
- XShm 요청을 파이프라인화하려면 각 진행 중 요청에 겹치지 않는 SHM 오프셋 또는 별도 슬롯을 할당한다. 같은 SHM 위치를 동시에 재사용하면 안 된다.
- 짧은 캡처 배치 창은 설정/적응형 옵션으로 실험하되, 서버 defer 타이머와 중복 대기하지 않도록 한다.

완료 기준: 작은 사각형 수백~수천 개 작업에서 Region 시간과 X 왕복 수가 줄고, 전체 화면 과잉 캡처·입력 지연이 악화되지 않는다. damage_subtract와 다음 변경 사이에 누락이 없는지도 검증한다.

### 4.6 캡처 쓰기 잠금과 인코딩 읽기 잠금의 경합을 줄인다 (P2)

근거: lib.rs의 apply는 screen 쓰기 잠금을 잡은 상태로 source.read와 X 응답을 기다린다. session.rs의 encode_update는 screen 읽기 잠금을 잡고 Interframe 및 전체 인코딩을 수행한다. 다중 클라이언트 인코딩 중 캡처가 기다릴 수 있다.

단계별 제안:

1. 캡처 스레드의 재사용 staging에 화면을 읽고, 짧은 쓰기 잠금으로 게시한다. 캡처는 한 생산자로 유지하고 크기/포맷 세대도 같이 게시한다.
2. 계측으로 읽기 잠금 경합이 큰지 확인한 후 변경 타일 또는 불변 프레임 스냅샷을 사용한다.
3. 스냅샷은 인코딩 작업 중 수명을 보장하고, 느린 클라이언트가 과거 프레임을 무한히 붙들지 못하게 제한한다.

트레이드오프: staging과 스냅샷은 복사량·메모리를 늘릴 수 있다. 특히 원본 버퍼를 JPEG에 직접 전달하는 최적화와 함께 설계해야 한다. 단일 클라이언트에서 잠금이 병목이 아니면 대규모 구조 변경을 하지 않는다.

완료 기준: 1/2/4개 클라이언트에서 잠금 대기와 캡처 지연 p95가 줄며, 해상도 변경 시 이전 stride/크기 사용과 프레임 찢어짐이 없다.

### 4.7 수신 버퍼의 앞부분 삭제와 작은 읽기 비용을 줄인다 (P1)

근거: 서버 session.rs의 Conn과 클라이언트 lib.rs의 Conn은 Vec::drain(..n)으로 메시지를 소비한다. 특히 클라이언트 Tight 디코더는 작은 control/length/palette 읽기를 반복하므로, 남은 데이터 이동 비용이 누적될 수 있다.

제안:

- 연속 버퍼에 읽기 위치를 두고 파서는 미소비 슬라이스를 본다. 일정 소비량을 넘을 때만 compact한다.
- 작은 디코더 읽기는 버퍼에서 충족하고, 큰 payload는 불필요한 중간 복사를 피하는 경로를 검토한다.
- 최대 메시지/압축 데이터 크기 제한과 취소 안전성을 유지한다.
- TLS 핸드셰이크로 전환할 때 이미 읽은 바이트의 소유권을 명확히 한다. 암호화 데이터와 평문 잔여 데이터를 잘못 섞지 않는다.

완료 기준: 같은 녹화 스트림의 파싱/디코딩 CPU 시간이 줄고, 분할 수신·여러 메시지 동시 수신·부분 EOF·TLS 전환 결과가 동일하다.

### 4.8 뷰어에서 JPEG를 목적 포맷과 stride로 직접 해제한다 (P1)

근거: tight/decoder.rs는 JPEG를 RGB Vec로 해제한 뒤 별도 픽셀 Vec로 변환하고 fb.put_rect로 복사한다. jpeg.rs는 호출마다 Decompressor를 생성한다.

제안:

- 연결의 디코더 상태에서 JPEG 핸들을 재사용한다.
- 일반적인 BGRX/RGBX 포맷에서는 목적 프레임버퍼의 사각형과 원래 stride로 직접 출력한다.
- 다른 포맷은 재사용 변환 버퍼로 처리한다. 입력 JPEG의 크기와 출력 영역 경계를 확인한다.
- 파싱과 네트워크 순서를 먼저 유지한다. 병렬 디코딩은 후순위로 두며 겹치는 사각형, CopyRect, 4개 zlib 스트림 의존성을 보존해야 한다.

완료 기준: 동일 JPEG 결과의 채널 배치와 화면이 일치하고, 녹화 재생에서 디코딩 시간·할당량이 감소한다.

### 4.9 뷰어를 damage 기반으로 갱신한다 (P1)

근거: conn.rs의 copy_rects는 변경 영역만 SharedScreen으로 옮기지만 window.rs의 render는 매번 가시 영역 전체를 softbuffer로 복사한다. 알림 중복 억제는 이미 있으므로 새로 구현할 필요가 없다.

제안:

- 변경 영역을 알림과 별도로 누적하고, 렌더 시 필요한 영역을 가져온다. 알림이 합쳐져도 damage는 사라지면 안 된다.
- softbuffer의 실제 버퍼 보존/age 규칙을 확인하고, 현재 버퍼에 필요한 과거 damage까지 합쳐 복사한다. 보존을 보장할 수 없으면 전체 재그리기를 유지한다.
- 리사이즈, 스크롤/오프셋 변경, 화면 노출, 연결 바·스크롤 바 상태 변경은 별도의 damage 또는 전체 무효화로 처리한다.
- SharedScreen 잠금 대기와 유지 시간을 측정하고, 필요 시 짧은 영역 복사나 제한된 프레임 교환을 사용한다.
- CPU 복사가 여전히 지배적인 경우 GPU 텍스처 부분 업로드를 별도 백엔드로 검토한다. 초기에는 softbuffer 경로를 유지한다.

완료 기준: 작은 커서/텍스트 변경에서 전체 화면 복사가 줄며, 창 가림/복원·부분 업데이트·리사이즈·연속 프레임에서 잔상이 없다.

### 4.10 Tokio 작업, 전송 및 역압을 함께 조정한다 (P2)

근거: async send_update 안에서 encode_update가 동기 실행되고 rayon::scope 완료를 기다린다. 업데이트 전체를 Vec에 만든 뒤 write_all/flush한다. 해당 세션은 쓰기 완료를 기다리는 동안 정상 이벤트 루프로 돌아오지 않는다.

제안:

- 먼저 Tokio 실행기 지연과 소켓 대기를 측정한다. CPU 작업은 상한이 있는 전용 작업자/블로킹 실행 경로로 옮기는 방안을 검토한다.
- 연결마다 무제한 스레드 풀을 만들지 않고 동시 인코딩 작업 수와 대기 작업 수를 제한한다.
- 전송 지연이 크면 순서를 보장하는 단일 writer와 제한된 전송 큐를 검토한다. Fence·리사이즈·SyncNext 경계는 반드시 유지한다.
- 큐가 차면 인코딩하기 전 수정 영역을 합쳐 최신 화면을 선택한다. 이미 압축한 업데이트는 zlib 스트림 및 클라이언트 상태를 진행시켰으므로 임의로 버리지 않는다.
- 부분 쓰기 중인 RFB 메시지의 중간에 입력 응답/Fence를 삽입하지 않는다. 스트리밍 전송은 헤더 수·LastRect·실패 처리까지 설계한 뒤 적용한다.
- TLS flush는 무조건 제거하지 않는다. 핸드셰이크/상호작용 경계의 즉시 전송을 지키면서 작은 메시지 병합 효과를 별도로 측정한다.

완료 기준: 대역폭 제한 및 느린 클라이언트에서도 큐 메모리가 제한되고, 빠른 클라이언트와 입력 처리의 p95 지연이 악화되지 않는다. 연결 해제·부분 쓰기·Fence 순서가 유지된다.

### 4.11 입력과 포인터 경로의 불필요한 적체를 줄인다 (P2)

근거: 입력 주입은 std::sync::mpsc::channel의 별도 스레드에서 처리한다. X11 캡처 루프는 pointer를 동기 query_pointer로 조회하며, 그 주기가 damage 이벤트 빈도와도 연결된다.

제안:

- 입력 큐의 길이와 이벤트 나이를 측정한다. 버튼 상태가 같은 연속 순수 이동만 합치고 최종 위치를 유지한다.
- 키 입력, 버튼 누름/해제, 휠, 드래그 경계 및 명령의 순서는 보존한다. 그리기/원시 이동을 요구하는 동작은 이동 병합을 제한하거나 끌 수 있게 한다.
- 포인터 조회를 경과 시간 기준으로 제한해 damage가 잦다고 과도하게 요청하지 않도록 한다.
- 단순히 폴링 간격을 늘리지 않고 원격 커서 표시 지연 및 idle CPU를 함께 측정한다.
- TLS는 기존에 읽기 대기 중 잠금 해제가 구현되어 있다. 제어 레코드/부분 레코드 수신 시 쓰기 지연이 관측될 때만 비동기 단일 I/O 소유자 구조를 검토한다.

완료 기준: 이벤트 폭주 뒤 오래된 마우스 이동이 재생되지 않고 키/버튼 누락이 없다. TLS on/off 및 idle 상태에서도 입력 응답이 유지된다.

### 4.12 화면을 덜 처리하는 추가 전략 (P2)

- Interframe은 이미 구현되어 있다. 타일별 버전/해시는 여러 클라이언트에서 중복 비교가 비쌀 때만 검토한다. 해시만으로 무손실 동일성을 단정하지 말고, 불확실한 경우 비교하거나 다시 전송한다.
- CopyRect 서버 전송은 스크롤·창 이동의 큰 이득 후보지만 XDamage는 이동 원본 좌표를 직접 주지 않는다. 검증된 이동 감지 또는 소스 정보가 있어야 하며 손실 영역·ALR·클라이언트 요청 영역·복사 순서도 함께 추적한다.
- 변경 영역을 줄이는 최적화와 영역 병합은 반대 효과가 날 수 있다. CPU·왕복·전송량을 함께 평가한다.
- GPU 표시, 프레임 공유, 동일 설정 클라이언트의 JPEG 공유는 측정 후 검토한다. 연결별 zlib 상태와 인코딩 설정이 다르므로 전체 Tight 바이트를 무조건 공유하지 않는다.

## 5. 인코더 개선과의 연결

진행 중인 libjpeg-turbo 도입 작업과 중복 수정하지 않고 다음 인터페이스를 맞춘다.

1. 서버 원본 BGRX/RGBX + stride를 인코더가 받을 수 있게 한다.
2. JPEG 선택 전 전체 클라이언트 포맷 변환을 피한다.
3. 작업자별 JPEG 핸들/출력/변환 버퍼를 재사용한다.
4. 원본 입력의 수명과 화면 잠금 전략을 함께 결정한다.
5. 프레임별 lossy 기록의 소비 책임을 서버/인코더 사이에 명시한다.

화질·서브샘플링을 낮추는 적응형 모드는 처리 경로 최적화와 별도로 평가하고 사용자 설정을 존중한다.

## 6. 구현 순서와 중단 기준

- 1단계: 구간별 프로파일, ALR 기록 수명, 기준 워크로드와 장시간 메모리 측정.
- 2단계: copy_region 임시 버퍼 제거, SHM 직접 행 복사, 수신 소비 커서. 서로 독립된 작은 변경으로 진행.
- 3단계: 커서 drawn 선택 갱신, damage 일괄 정규화, 캡처 영역 그룹화, 뷰어 JPEG 직접 출력.
- 4단계: softbuffer 부분 갱신. 플랫폼 보존 규칙을 확인하기 전에는 적용하지 않음.
- 5단계: 잠금/CPU 작업/전송 큐 구조 개선. 계측에서 실제 경합이나 적체가 확인된 항목만 선택.
- 6단계: CopyRect, GPU, 타일 공유 등 큰 변경은 앞 단계 이후 병목이 남을 때 별도 설계.

각 변경에서 목표 구간의 비용이 감소하지 않거나 화면 정합성·입력 지연·메모리가 악화되면 확대 적용하지 않는다. 추정 개선율을 합산해 전체 향상률로 발표하지 않는다.

## 7. 검증 계획

모든 벤치마크는 향후 구현 작업에서 별도 실행한다. 이 문서 작성 시에는 실행하지 않았다.

### 7.1 조건과 워크로드

- release 빌드, CPU/코어 제한, libjpeg-turbo 빌드/SIMD 여부, JPEG 품질·서브샘플링·CL·스레드·defer·ALR·Interframe·TLS를 기록한다.
- 1920×1080 및 3840×2160, 정지 화면, 터미널 스크롤, 창 이동, 다수 작은 damage, 사진/영상, 포인터 폭주를 각각 측정한다.
- 1/2/4 클라이언트, 커서 확장 지원/미지원 혼합, localhost/LAN/대역폭 제한, TLS on/off를 포함한다.
- Xvfb/Xorg 및 SHM/GetImage를 구분한다. TurboVNC는 내장 X 서버, MiniVNC는 외부 캡처이므로 서버 CPU만과 X 서버 포함 전체 CPU를 모두 보고한다.
- 같은 뷰어로 두 서버를 비교하고, 같은 녹화 스트림으로 뷰어 디코더를 비교한다. 종단 GUI 평가는 별도로 실행한다.

### 7.2 도구와 판정

기존 tools/rfb-bench는 live 업데이트/s·Mpixels/s·Mbits/s, 녹화 및 재생 디코딩 측정의 출발점이다. 현재 live 경로는 Vnc/None을 선택하므로 TLS 성능 측정에는 뷰어 또는 도구의 추가 지원이 필요하다. replay는 창 렌더링 비용을 포함하지 않는다. 업데이트/s는 프레임 병합·사각형 분할에 영향을 받으므로 실제 표시 프레임·지연과 함께 본다.

- 예열 후 같은 작업을 반복 실행해 중앙값과 분산을 보고하고, 최초 전체 화면 전송은 분리한다.
- 4K 32bpp 버퍼 한 개는 약 33.2MB(31.6MiB)이다. 초당 60회 전체 버퍼 쓰기는 약 1.99GB/s이며 읽기·다른 복사는 별도이다. 이를 복사량 해석에만 사용하고 가능한 FPS로 환산하지 않는다.
- 단순 복사·포맷 변환·영역 연산은 픽셀/영역 정합성 검사와 기존 테스트를 사용한다.
- 수신 버퍼는 임의 분할/합쳐진 메시지·부분 EOF·길이 제한 회귀를 검증한다.
- 큐·잠금 변경은 느린 연결, 리사이즈, 연결 종료, Fence, CopyRect, TLS, ALR 복원과 장시간 메모리를 검증한다.
- 결과 표에는 순수 인코딩 시간, 캡처 시간, 잠금 대기, 전송 대기, 뷰어 시간, 지연 분포, CPU/RSS, 전송량을 분리한다.
