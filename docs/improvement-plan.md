# MiniVNC 처리 속도 개선 계획

- 최초 작성: 2026-11-03. 다른 에이전트가 소스를 정적으로 분석해 작성했다.
- 검토·갱신: 2026-11-03. M7을 마치는 시점에 코드와 실측으로 검토했다.
- 갱신: 2026-11-04. 뷰어 부분 표시의 전체 무효화 조건(최소화 복원, 창 이동)을 보강하고, 처리 속도와 별개로 Windows 뷰어의 연결 대화상자와 이후 사용성 개선 계획을 7절에 더했다.

분석 대상은 `D:\dev\minivnc`의 Rust 구현과 `D:\dev\minivnc\turbovnc`(TurboVNC 3.3.2 소스)이다. 범위는 서버 캡처·동시성·전송·영역 처리와 클라이언트 수신·디코딩·렌더링이다.

## 1. 결론

정적 분석이 제안한 항목은 실측에 따라 셋으로 나눈다.

- **이미 적용됨**: M7 개발 중에 같은 문제를 측정으로 찾아 고쳤거나, 이번 검토에서 바로 고친 항목.
- **적용 가능**: 근거가 코드에서 확인되고, 변경 범위가 작으며, `rfb-bench`나 `-profile`로 효과를 측정할 수 있는 항목. 아래 권장 순서대로 하나씩 측정하며 적용한다.
- **적용 어려움·보류**: 측정에서 병목이 아니었거나, 프로토콜 순서·수명 관리 위험에 비해 이득이 불확실하거나, 다른 마일스톤의 범위인 항목.

M7 완료 시점의 실측(2절)에서 MiniVNC 서버는 TurboVNC 3.3.1 Xvnc와 비교해 다음과 같았다.

- 인코딩 처리량은 대부분 89~142%였다. 영상의 무손실 CL0만 75%(쓰기 대기 포함)였고, 쓰기 대기를 빼면 108%였다.
- 대역폭은 모든 영상 조건에서 ±4% 안이었다.

남은 차이는 다음 두 가지다.

- **외부 캡처 비용**: Xvfb와 MiniVNC 서버를 합친 CPU가 Xvnc의 약 1.5~2배였다.
- **무손실 대용량 업데이트의 전송 대기.**

따라서 아래 "적용 가능" 항목은 처리량 목표를 맞추기 위한 것이 아니라 CPU와 복사량을 줄이기 위한 것이다.

3.2의 항목을 권장 순서대로 적용한 결과는 3.4에 있다. 10개 중 9개를 적용했고 8번은 보류했다. 최종 측정은 `docs/bench.md`에 있다.

## 2. 측정 근거 (M7 완료 시점)

- 환경: WSL2 Ubuntu 26.04(24 vCPU)에서 1920x1080 디스플레이와 `-deferupdate 1`을 썼다.
- 서버:
  - TurboVNC 3.3.1 Xvnc(`TVNC_PROFILE=1`)
  - MiniVNC 서버(Xvfb 캡처, `-profile`, 인코딩 스레드 4)
- 측정: 같은 머신의 `rfb-bench`가 TurboVNC 뷰어처럼 CU와 Fence를 쓰며 15초씩 측정했다.
- 처리량: 두 서버 모두 프로파일의 "Encode" 시간(쓰기 대기 포함)을 Mpixel당으로 환산해 비교했다.

  - 영상: MiniVNC(Xvfb + 서버) 17~22%, Xvnc 8~14%.

## 3. 검토 결과 요약

### 3.1 이미 적용됨

| 원래 항목 | 적용 내용 | 근거·효과 |
| --- | --- | --- |
| 4.2 ALR이 꺼져 있어도 lossy 기록 누적 | 지적이 맞았다(M7에서 생긴 버그). 이번 검토에서 업데이트마다 `take_lossy`로 기록을 비우고, ALR이 켜졌을 때만 영역에 반영하도록 고쳤다(`session.rs` `encode_update`). | 연결 수명 동안 커지던 메모리 누적이 없어졌다. |
| 4.3 SHM 결과의 `to_vec` 임시 복사 | `get_image`를 없앴다. SHM 응답을 받으면 공유 메모리의 행을 프레임버퍼로 바로 복사한다(`read_rects`, `put_image`). | 캡처의 사각형별 임시 할당이 없어졌다. |
| 4.5 DamageNotify마다 `Region::union`, 사각형마다 동기 X 왕복 | XFIXES가 있으면 DAMAGE를 `NON_EMPTY`로 받는다. `DamageSubtract`로 XFixes 영역에 옮긴 뒤 한 번에 읽는다. `ShmGetImage`는 사각형마다 겹치지 않는 SHM 오프셋을 주고 모두 보낸 뒤 응답을 기다린다. 세그먼트가 차면 그때까지를 먼저 읽는다. | x11perf 텍스트 부하에서 갱신이 초당 5.7회에서 68회로 올랐다(TurboVNC 41~74회). 문서가 지적한 SHM 오프셋 충돌 조건을 지켰다. |
| 4.1 프로파일의 encode 시간에 쓰기 대기 포함 | `-profile`이 쓰기 대기 포함 시간(TurboVNC와 같은 기준)과 "without writing"(순수 생성 시간)을 함께 기록한다. | 무손실 CL0의 처리량 미달(75%)이 인코딩이 아니라 쓰기 대기 때문임을 구분했다(쓰기 제외 108%). |
| 5.1 서버 원본 BGRX/RGBX를 JPEG에 직접 전달 | `jpeg::Layout`(Rgb/Rgbx/Bgrx)을 추가했다. 32bpp 화면은 픽셀 변환 없이 행만 이어 붙여 넘긴다. | `send_jpeg`의 픽셀 단위 언팩(프로파일 21%)이 없어졌다. |
| (인코더) libjpeg-turbo 도입 | Linux는 libjpeg-turbo 3을 소스에서 정적 빌드한다(CMake, NASM). 다른 플랫폼의 순수 Rust 경로는 jpeg-encoder AVX2를 쓴다. | JPEG 인코딩이 TurboVNC와 같은 수준이 되었다(1.76 대 1.78 ms/Mpixel). |
| (인코더) 팔레트 색상 계수 | 팔레트 색인을 고정 크기 개방 주소 표로 바꾸고, 개수만 늘면 원소를 옮기지 않는다. 팔레트 순서는 TurboVNC와 같다. | testsrc 무손실 처리량이 45%에서 92%로 올랐다. |
| (기존 기능) Tight 병렬 인코딩, Interframe, ALR, CU/Fence, 뷰어 요청 파이프라이닝 | M5와 M7에서 구현했다. 문서의 2절 목록대로 중복 구현하지 않는다. | — |

### 3.2 적용 가능 (권장 순서)

| 순서 | 항목 | 원래 절 | 이유 | 측정 방법 |
| --- | --- | --- | --- | --- |
| 1 | `copy_region`의 임시 `Vec` 제거 | 4.3 | 코드에서 확인했다(사각형마다 행을 모은 뒤 `put_rect`). 프레임버퍼 사이의 행 복사로 바꾸면 되는 작은 변경이다. | 캡처 스레드 memcpy 비율(perf). 영상 부하에서 현재 서버 CPU의 약 1/4 |
| 2 | JPEG 입력에 프레임버퍼 stride 전달 | 5.1, 5.3 | libjpeg-turbo는 pitch를 받으므로 행을 이어 붙이는 복사가 필요 없다. 순수 Rust(jpeg-encoder)는 연속 버퍼가 필요하므로 그 경로는 그대로 둔다. | `-profile`의 "without writing" 시간 |
| 3 | JPEG 압축·해제 핸들 재사용 | 4.8, 5.3 | `turbojpeg::compress`와 `Decompressor::new`를 호출마다 만든다. 인코더 작업(띠)별·디코더별로 보관한다. | 작은 JPEG 사각형이 많은 low/medium 프리셋 |
| 4 | 뷰어 JPEG를 목적 포맷으로 직접 해제 | 4.8 | 디코더가 RGB 버퍼, 픽셀 버퍼, `put_rect`의 세 단계를 거친다. 뷰어는 RGB888(BGRX)을 요청하므로 libjpeg-turbo가 목적 사각형에 바로 쓸 수 있다. 다른 포맷은 기존 경로를 쓴다. | `rfb-bench -record` 후 `-replay`의 ms/update |
| 5 | 수신 버퍼 소비 위치(커서) 도입 | 4.7 | 서버와 클라이언트 `Conn`이 `Vec::drain(..n)`으로 앞부분을 지운다. Tight 디코더의 작은 읽기마다 남은 데이터가 이동한다. 일정량 이상 소비했을 때만 앞으로 당긴다. TLS 전환 시점에는 버퍼가 비어 있음을 이미 검사하므로 그 조건을 유지한다. | `rfb-bench -replay`(클라이언트), 무손실 프리셋 |
| 6 | JPEG 판단 전 클라이언트 포맷 변환 생략 | 5.2 | `send_subrect`는 사각형 전체를 클라이언트 포맷으로 변환하고 픽셀 값 배열을 만든 뒤 색상을 센다. JPEG로 갈 때는 둘 다 버려진다. TurboVNC처럼 서버 픽셀에서 색을 세면, 두 포맷이 같은 흔한 경우 변환이 없어진다. 팔레트 결과가 같아야 하므로 TurboVNC의 `FillPalette` 입력과 비교 검증이 필요하다. | perceptual/medium 프리셋의 순수 인코딩 시간 |
| 7 | 포인터 조회 파이프라이닝·주기 제한 | 4.11 일부 | 캡처 루프가 반복마다 동기 `QueryPointer` 왕복을 한다. 4.3 수정 뒤에는 X 서버가 바쁠 때 남은 왕복의 대부분이다. 요청을 먼저 보내고 응답은 다음 단계에서 받거나, 10ms 경과 기준으로 제한한다. | x11perf 부하의 갱신 수와 커서 표시 지연 |
| 8 | 소프트웨어 커서용 `drawn` 버퍼 선택 갱신 | 4.4 | 커서 모양 인코딩을 받지 않는 클라이언트가 없으면 `drawn` 복사가 필요 없다. 측정상 비용이 작으므로(1번과 같은 memcpy의 절반) 1번 뒤에도 의미가 있을 때만 한다. 커서 협상 변경·리사이즈 때 다시 채워야 한다. | 1번과 같음 |
| 9 | 구간별 계측 확장 | 4.1 | 캡처 대기, 화면 잠금 대기, 영역·Interframe 시간을 `-profile`에 더한다. 6절의 보류 항목(잠금 분리, 전송 큐)을 재검토할 근거가 된다. | 계측 on/off 오버헤드 |
| 10 | 뷰어 damage 기반 표시 | 4.9 | `render`가 매번 가시 영역 전체를 softbuffer에 복사한다. softbuffer의 `buffer_age` 규칙을 지킬 때만 부분 복사하고, 보장되지 않으면 전체 복사를 유지한다. 플랫폼별(Windows/X11/Wayland) 확인이 필요해 가장 마지막에 한다. | 뷰어 CPU, 4K 창에서 작은 변경 |

### 3.3 적용 어려움·보류

| 항목 | 원래 절 | 판단 근거 |
| --- | --- | --- |
| 캡처 쓰기 잠금과 인코딩 읽기 잠금 분리(staging, 스냅샷) | 4.6 | 측정에서 잠금 경합의 증거가 없었다. 영상 부하의 갱신 수는 화면 변화 속도(30fps)로 정해졌다. staging은 복사를 하나 더 만든다. 3.2의 9번 계측으로 다중 클라이언트 경합이 확인될 때 재검토한다. |
| Tokio 작업 분리, 전송 큐, 스트리밍 전송 | 4.10 | Fence·SyncNext·LastRect 순서와 zlib 스트림 상태 때문에 위험이 크다. 측정상 "other" 시간은 화면 변화 간격이었고 실행기 지연이 아니었다. 무손실 대용량 업데이트의 쓰기 대기는 네트워크 대역폭 문제다. 느린 링크 측정 결과가 있을 때 재검토한다. |
| 입력 이벤트 병합 | 4.11 | TurboVNC는 입력을 병합하지 않는다. 그리기 앱의 궤적이나 드래그의 의미가 바뀔 수 있다. 입력 큐 적체가 관측되지 않았다. 포인터 조회 개선만 3.2의 7번으로 분리했다. |
| `Region` 선형 병합, 캡처 영역 비용 모델 | 4.5 일부 | `NON_EMPTY`와 XFixes 영역 읽기 뒤에는 이벤트마다 union하지 않는다. 프로파일에서 `rfb_region`은 0.5% 미만이었다. 영역 비용 모델은 과잉 캡처를 막는 이득이 측정되지 않았다. |
| SHM을 인코더에 바로 노출하는 zero-copy | 4.3 | 다음 X 요청이 공유 메모리를 덮어쓴다. 화면 잠금 수명과 엮여 위험하며, 원래 문서도 후순위로 두었다. |
| 서버 CopyRect 생성, 타일 해시, GPU 표시, JPEG 결과 공유 | 4.12 | XDamage는 이동 원본을 알려 주지 않는다. 스크롤 감지 CopyRect는 M8의 실험 항목이다. 클라이언트마다 zlib 상태와 설정이 달라 결과를 공유할 수 없다. |
| 적응형 화질 저하 | 5 | 사용자 설정을 바꾸는 기능이므로 처리 경로 최적화와 분리한다(원래 문서와 같은 판단). |

### 3.4 적용 결과 (2026-11-04)

3.2의 순서대로 적용하고 항목마다 측정했다. 처리량 측정의 반복 편차는 ±5~8%다. 그래서 그보다 작은 차이는 "잡음 범위"로 적었다.

| 순서 | 결과 | 구현 | 측정 |
| --- | --- | --- | --- |
| 1 | 적용 | `Framebuffer::copy_rect_from`으로 프레임버퍼 사이를 행 단위로 바로 복사한다(`copy_region`). | 캡처 적용 시간은 변경당 0.34~0.38 ms. |
| 2 | 적용 | `Framebuffer::rect_bytes`와 stride를 `jpeg::Image`로 넘긴다. libjpeg-turbo는 화면을 그 자리에서 읽고, 순수 Rust 경로는 내부에서만 행을 잇는다. | 3·6번과 함께 영상 perceptual 약 10% 단축(1.49~1.61 → 1.40~1.41 ms/Mpixel). |
| 3 | 적용 | `JpegCompressor`(띠마다 하나), `JpegDecompressor`(디코더마다 하나)가 libjpeg-turbo 핸들을 재사용한다. | 2번과 같음. |
| 4 | 적용 | 32bpp 프레임버퍼면 JPEG를 사각형 자리에 바로 해제한다(`decompress_into`). 다른 포맷은 기존 경로를 쓴다. | JPEG 녹화 재생 4.15 → 2.60 ms/update(5번 포함). |
| 5 | 적용 | `rfb_proto::wire::RecvBuf`가 소비 위치를 두고, 소비분이 절반 이상일 때 새 데이터가 들어오면 앞으로 당긴다(서버·클라이언트 공용). | 무손실 녹화 재생 1.68 → 1.51 ms/update. |
| 6 | 적용 | 서버와 클라이언트의 bpp·채널 크기가 같고 16bpp 이상이면, TurboVNC `FastFillPalette`처럼 서버 픽셀(변환이 있으면 채널 마스크 적용)로 색을 센다. 보낼 색만 `Translator::translate_pixel`로 바꾼다. JPEG로 가는 사각형은 변환하지 않는다. | 2번과 같음. 처음 구현은 Full 경로에서 픽셀 값을 두 번 만들어 무손실이 느려졌다. 변환이 항등이면 다시 만들지 않게 고쳤고, 이후 무손실은 개선 전과 잡음 범위 안에서 같다. |
| 7 | 적용 | `QueryPointer`를 10 ms 경과 때만 보내고, 손상 영역 요청과 함께 보낸 뒤 응답을 받는다. | x11perf 부하의 갱신 수가 초당 68회에서 101회로 올랐다. |
| 8 | 보류 | — | 1번 이후 캡처 적용은 변경당 약 0.36 ms(초당 120회에 CPU 약 4%)다. 그중 `drawn` 복사는 절반 이하다. 연결별 커서 협상 추적에 따르는 잔상 위험에 비해 이득이 작다. |
| 9 | 적용 | `-profile`이 세션별 화면 잠금 대기·Interframe 시간과 캡처 스레드의 변경당 읽기·적용 시간을 기록한다. | 잠금 대기는 업데이트당 0.01~0.05 ms로 작다. 6절(보류)의 잠금 분리를 미룬 근거가 된다. |
| 10 | 적용 | RFB 스레드가 바뀐 사각형을 `SharedScreen`에 기록한다. 창은 같은 화면을 보이고 버퍼 age가 알려 주는 이전 프레임들의 변경이 모두 남아 있을 때만, 그 사각형만 복사하고 `present_with_damage`로 표시한다. 그 밖에는 전체를 복사한다. 컴포지터 없이 창 노출 시 다시 그려야 하는 X11(Xlib/Xcb)에서는 쓰지 않는다. | Windows에서 움직이는 패턴을 캡처해 잔상이 없음을 확인했고, 5초에 약 300회 부분 표시했다. Wayland는 확인하지 못했다. 이후 Windows에서 창 내용이 사라지는 두 경우를 찾아 전체 표시로 바꿨다. 최소화했다가 같은 크기로 복원할 때(`Resized`)와, 모니터 밖에 있던 부분을 창 이동으로 화면 안에 들일 때(`Moved`)다. 두 경우 모두 바뀐 사각형만 그려 나머지가 검게 남았다. |

## 4. 적용 가능 항목의 세부 지침

정적 분석의 제안 가운데 3.2에 남긴 항목의 지침이다.

- **`copy_region`, `put_image`**: 16/32bpp, 행 패딩, 리사이즈, SHM이 없을 때의 GetImage 경로에서 픽셀이 기존과 같아야 한다(`loopback`과 X11 수동 확인).
- **JPEG stride·핸들 재사용**
  - 띠별 작업(`Job`)이 자기 핸들을 갖고, 스레드 간에 공유하지 않는다.
  - 순수 Rust 경로는 행을 이어 붙인 현재 방식을 유지한다.
  - `jpeg.rs`의 두 백엔드 상호 운용 테스트를 유지한다.
- **뷰어 직접 해제**
  - JPEG의 크기가 사각형과 같은지 먼저 확인한다(현재 `decompress`의 검사 유지).
  - 병렬 디코딩은 하지 않는다. 네 zlib 스트림과 사각형 순서에 의존한다.
- **수신 커서**
  - 메시지 최대 길이 제한, 부분 수신, 여러 메시지 동시 수신, EOF의 동작이 같아야 한다.
  - 클라이언트의 TLS 전환 조건(버퍼가 비어 있음)을 유지한다.
- **JPEG 판단 전 변환 생략**
  - 무손실 경로의 바이트 출력은 바뀌면 안 된다(`tight_roundtrip` 비교).
  - 색 수 계산은 TurboVNC `FillPalette`와 같은 입력(서버 픽셀)을 써야 팔레트 순서가 같다.
- **포인터 조회**: 커서 위치 표시 지연과 idle CPU를 함께 측정한다. 단순히 폴링 간격을 늘리지 않는다.
- **`drawn` 선택 갱신**: 커서 인코딩을 쓰는 클라이언트와 쓰지 않는 클라이언트가 섞인 경우, 연결 종료, 리사이즈, 커서 숨김 전환에서 잔상이 없어야 한다.
- **뷰어 부분 표시**: 창 가림·복원, 최소화 복원, 창 이동(모니터 밖 영역), 스크롤, 연결 바 표시 전환, 리사이즈를 전체 무효화로 처리한다. 창을 끄는 동안에는 이동마다 전체를 다시 그리지만, 이동이 끝나면 부분 표시로 돌아간다.

각 변경에서 목표 구간이 줄지 않거나 화면 정합성·입력 지연·메모리가 나빠지면 적용하지 않는다. 개선율을 합산해 전체 향상률로 발표하지 않는다.

## 5. 검증 방법

- **서버**
  - `docs/bench.md`에 기록한 절차(WSL, 1920x1080, `-deferupdate 1`, mpv·x11perf 부하)로 두 서버를 같은 `rfb-bench`로 측정한다.
  - 처리량은 `-profile`의 Mpixel당 시간으로 비교한다.
  - CPU는 X 서버를 포함한 값과 서버만의 값을 함께 보고한다. TurboVNC는 X 서버 내장이고 MiniVNC는 외부 캡처이기 때문이다.
- **클라이언트**
  - `rfb-bench -record`로 녹화한 같은 스트림을 `-replay`로 디코딩해 비교한다.
  - replay는 창 렌더링을 포함하지 않으므로, 3.2의 10번은 뷰어에서 따로 측정한다.
- **반복**: 예열 뒤 같은 작업을 반복해 중앙값을 쓰고, 최초 전체 화면 전송은 제외한다(`rfb-bench`가 이미 제외한다).
- **장시간**: ALR on/off에서 장시간 RSS가 안정적인지 확인한다(3.1의 4.2 수정 확인).

## 7. 뷰어 사용성: Windows 연결 대화상자 (2026-11-04)

처리 속도와 별개인 사용성 변경이다. 이전 Windows 뷰어는 콘솔 프로그램이어서 다음 문제가 있었다.

- 비밀번호, Unix Login 사용자·비밀번호, 인증서 확인을 콘솔에서 물었다.
- 탐색기에서 실행하면 콘솔 창이 함께 떴다.
- 콘솔(터미널)을 닫으면 뷰어도 끝났다.

### 7.1 적용 내용

| 항목 | 내용 |
| --- | --- |
| 실행 형태 | Windows 빌드는 GUI 서브시스템(`windows_subsystem = "windows"`)이다. 콘솔을 만들지 않으므로 터미널을 닫아도 뷰어가 끝나지 않는다. 테스트 빌드는 콘솔을 유지한다. |
| 연결 대화상자 | 서버와 비밀번호를 받는다. 명령행이나 `.turbovnc` 파일로 준 서버는 입력한 그대로 채운다(`Options::server`). 서버와 비밀번호(`-Password`, `-PasswordFile`)를 모두 주었거나 `-listen`이면 띄우지 않는다. 취소하면 종료 코드 0으로 끝난다. |
| 비밀번호 | 대화상자의 비밀번호는 `-Password`와 같은 VNC 비밀번호다. 비워 두면 서버가 VNC 인증을 고를 때 서버 이름을 읽기 전용으로 보이는 비밀번호 대화상자를 띄운다. |
| 그 밖의 질문 | Unix Login/Plain은 사용자·비밀번호 대화상자를 쓴다. X.509 인증서 확인은 예/아니요 메시지 상자이고, 기본값은 아니요다. `rfb-client`의 `ask_password`·`ask_login`·`confirm` 훅만 바꿨다. |
| 오류·도움말 | 연결·인증 오류는 메시지 상자로 보인다. `-help`와 옵션 오류는 뷰어를 실행한 콘솔이 있으면(`AttachConsole`) 그곳에 출력하고, 없으면 메시지 상자로 보인다. |
| 로그 | 콘솔이 없으므로 stderr를 리디렉션했을 때(`2> FILE`)만 남는다. |
| 리소스 | 대화상자 템플릿을 `minivnc-viewer.rc`에 두었다. 매니페스트(`minivnc-viewer.manifest`)로 Common Controls 6 테마와 PerMonitorV2 DPI 인식을 켰다. 새 의존성은 없다(`windows-sys` 기능만 추가). `rpassword`는 Windows가 아닌 빌드에서만 쓴다. |
| Linux | 바뀌지 않았다. 콘솔에서 묻는다. |

검증(Windows, 테스트 패턴 `minivnc-server`와 VNC 비밀번호):

- 서버 인수 + 대화상자 비밀번호, 인수 없음, 빈 비밀번호 뒤 비밀번호 대화상자, 틀린 비밀번호(오류 상자, 종료 코드 1), 취소(종료 코드 0)를 확인했다.
- 콘솔 출력(리디렉션과 대화형 콘솔)과 콘솔 없는 실행의 오류 상자도 확인했다.
- Linux 빌드는 확인하지 못했다(CI에서 확인).

알려진 제약:

- 터미널에서 실행하면 셸이 뷰어 종료를 기다리지 않고 바로 프롬프트로 돌아온다.
- `-via`의 ssh가 비밀번호를 물으면 ssh가 별도 콘솔 창을 연다.

### 7.2 향후 개선 계획

우선순위가 높은 것부터 적는다. 범위가 커지는 항목은 사용자 확인 후 진행한다.

| 순서 | 항목 | 내용·판단 |
| --- | --- | --- |
| 1 | 최근 접속 서버 기록 | 서버 입력란을 콤보 상자로 바꾸고 최근 서버를 보인다. 저장 위치(TurboVNC 뷰어는 `~/.vnc` 아래)와 개수를 정해야 한다. 사용자 요청으로 보류했다. |
| 2 | 로그 파일 옵션 | 콘솔이 없을 때 진단 수단이 리디렉션뿐이다. `-Log=FILE` 같은 옵션이나 `%LOCALAPPDATA%` 아래 기본 로그를 검토한다. |
| 3 | 비밀번호 저장 | 연결 대화상자의 "비밀번호 저장"으로 TurboVNC 형식 비밀번호 파일을 쓰거나 Windows 자격 증명 관리자를 쓴다. 평문에 가까운 VNC 비밀번호 파일의 위험을 함께 알린다. |
| 4 | 대화상자의 주요 옵션 | 인코딩, JPEG 화질·서브샘플링, 스케일, 보기 전용 같은 TurboVNC Options 대화상자의 일부를 연결 대화상자에서 고르게 한다. 지금은 명령행과 `default.turbovnc`로만 바꾼다. |
| 5 | Linux GUI 질문 | 터미널 없이(`.desktop`, `Terminal=false`) 실행하면 질문할 곳이 없다. zenity/kdialog 호출이나 자체 대화상자를 검토한다. |
| 6 | `-via` ssh 비밀번호 | ssh의 `SSH_ASKPASS`로 뷰어의 비밀번호 대화상자를 쓰게 하면 별도 콘솔 창이 필요 없다. Windows OpenSSH의 지원 범위는 확인이 필요하다. |
| 7 | 재연결 | 연결이 끊기면 오류 상자 뒤 끝나는 대신 다시 연결할지 묻는다. TurboVNC 뷰어의 동작을 먼저 확인해 맞춘다. |
